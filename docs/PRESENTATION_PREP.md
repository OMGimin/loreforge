# LoreForge — 코드를 설명하기 위한 준비 노트

**SKALA 4기 광주캠퍼스 G074 김지민 · 과제 2**

2026-10-22에 수업 PDF·오전 전사록·발표 공지와 실제 구현을 대조해 정리했다. 발표에서 읽는 대본은 [PRESENTATION.md](PRESENTATION.md)에 있다. 이 문서는 대본의 이유를 이해하고 코드 질문에 답하기 위한 자료다. 자료 작성과 본인의 설명 능력 확인은 구분한다. 아래 질문에 실제로 답해 본 결과는 아직 기록하지 않았다.

## 1. 교수님이 요구한 설명의 수준

수업 PDF의 **파일 10쪽(인쇄 번호 9)**은 과제 2에서도 “작성된 코드와 내용을 설명을 할 수 있어야 합니다”라고 명시한다. 오전 전사록에서는 AI 도구를 써도 코드와 하고자 한 일을 설명할 수 있어야 하며, “왜 이렇게 작성했냐”는 질문에 AI가 짜줬다는 답으로 끝내면 안 된다고 강조했다. 앞부분에서는 프로그램의 흐름, 폴더 구조, 파일별 역할부터 분석하라고 했다. 전사록은 자동 전사라 오기가 있으며, 이를 교정한 긴 인용문을 원문처럼 제시하지 않았다.

PDF **파일 13쪽(인쇄 번호 12)**의 평가표는 기능 구현 30점, 기술 요소 30점, 한계·트레이드오프 20점, PPT·발표 20점이다. 같은 입력의 전후 실측 비교 10점은 보너스다. 기술 목록에는 Multi-Agent·MCP·RAG·의존성 주입·LangSmith·모듈화·단위 테스트가 열거되어 있지만, 각 항목을 모두 필수 구현해야 한다는 문구는 확인되지 않았다. 구현한 기술의 역할과 미적용 이유를 정확히 설명하는 쪽으로 준비한다. 평가에서 개별 미적용 항목을 어떻게 반영하는지는 별도 판단 영역이다.

최신 전달 공지에 맞춰 앞 2분은 주제·태스크·결과, 뒤 3분 이내는 Agent Graph·MCP·RAG 관련 구현 판단을 설명한다. PDF 3쪽의 예전 일정 대신 전사록의 정정 및 최신 공지를 참고한다.

**설명할 수 있는 기준:** 기능 하나마다 입력이 무엇인지, 어느 코드가 처리하는지, 왜 그 방식인지, 어떤 결과를 내는지, 실패하거나 정확하지 않을 때 어떻게 되는지 말할 수 있어야 한다. 모든 줄을 암기할 필요는 없지만, 주요 함수에서 다음 단계로 넘어가는 이유는 알아야 한다.

## 2. 우선 전체 흐름을 한 번 따라가기

화면은 Vue가 담당한다. 요청을 받는 FastAPI 서버가 입력·실행 상태를 SQLite에 저장하고, OpenAI API를 호출한다. LangGraph는 생성·검토·수정의 순서를 제어한다. 결과의 본문·항목·관계·근거를 화면에서 함께 보여준다.

| 단계 | 하는 일 | 코드 |
|---|---|---|
| 원문 등록 | 입력 문단에 ID를 부여하고 저장 | `main.py`의 sources API, `documents.py` |
| 분석 | 설정 담당이 항목·관계·유지 조건 후보를 추출 | `main.py:104`의 `analyze`, `provider.py` |
| 기준 확정 | 분석 결과와 선택 조건으로 실행 당시 기준을 복사·저장 | `main.py`의 runs API |
| 실행 | 생성 또는 검토로 시작해 정해진 경로를 수행 | `workflow.py`의 `build_workflow` |
| 결과 탐색 | 본문, 검토 쟁점, 관계도, 근거 문단 표시 | 프런트엔드 및 `documents.py` |
| 채택·이어쓰기 | 생성 결과의 채택한 최종본만 다음 기준에 추가 | `main.py`의 decision·runs API |

**스냅샷**은 실행 당시의 기준을 보관한 복사본이다. 나중에 어떤 기준으로 그 판단이 나왔는지 복원하려고 사용한다. 검토 전용에서는 원문을 다시 쓰거나 자동 채택하지 않는다.

내 설명: “새 이야기는 키워드로 만들고, 기존 원고는 그대로 두고 문제부터 검토합니다. 실행할 때 기준을 고정해 저장하고, 결과마다 어느 문단을 근거로 했는지 연결했습니다.”

## 3. Agent Graph — 가장 먼저 이해할 코드

**화면 관계도와 Agent Graph는 다른 그래프다.** 화면 관계도의 노드는 인물·장소·사건이고, Agent Graph의 노드는 실행 단계다. 전자는 Cytoscape.js, 후자는 LangGraph를 사용한다.

`backend/workflow.py:86`부터 보면 네 개의 노드가 있다.

| 코드 | 뜻 |
|---|---|
| `StateGraph(State)` | 노드들이 주고받는 실행 상태의 틀을 지정 |
| `add_node("generate", generate)` | 이름과 실제 실행 함수를 등록 |
| `add_edge("generate", "review")` | 생성이 끝나면 검토로 이동 |
| `add_conditional_edges("review", route, ...)` | `route` 반환값에 따라 수정 또는 종료로 이동 |
| `add_edge("revise", "review")` | 수정 후 다시 검토 |
| `compile()` / `ainvoke(...)` | 실행 가능한 그래프를 만들고 비동기로 실행 |

`State`에는 `run`이 들어 있다. 이 안에 기준 문서, 초안, 수정본, 검토 이력, 미해결 쟁점, 사용량 등이 있다. 노드는 이를 읽고 변경한 뒤 반환한다. 상태를 LangGraph에 전달하는 것과 DB에 영구 저장하는 것은 별개이며, `save()`가 저장과 진행 이벤트 기록을 담당한다.

설정 분석은 이 그래프의 노드가 아니다. 최초 입력은 분석 API에서, 이어쓰기는 `execute()`의 준비 단계에서 분석한 뒤 그래프를 실행한다.

### 수정 조건을 말로 풀기

`workflow.py:71`의 `route()`는 다음 **세 조건을 모두 만족할 때만** 수정으로 보낸다.

1. 생성 모드다. 원문 검토 모드는 수정하지 않는다.
2. 아직 수정본이 없다. 이미 수정했다면 두 번째 수정은 하지 않는다.
3. 열린 쟁점 중 작성자 의도 확인 질문이 아닌 문제가 있다.

의도 확인 질문은 AI가 답을 정해 버리면 안 되므로 보존한다. 수정 후에도 열린 문제나 보존된 질문이 남으면 `finish()`가 `needs_attention`으로 끝낸다. 실행이 정상 종료된 것과 설정에 문제가 없는 것은 같은 의미가 아니다.

| 예시 | 다음 동작 |
|---|---|
| 첫 초안에 내부 모순 | 한 번 수정한 뒤 재검토 |
| 재검토에도 내부 모순 | 추가 수정 없이 확인 필요로 종료 |
| 첫 검토에 의도 질문만 있음 | 자동 수정 없이 질문을 남기고 종료 |
| 기존 원고 검토에서 문제 발견 | 원문 수정 없이 문제를 보여주고 종료 |

### 왜 역할을 나눴나

설정 담당은 추출, 창작 담당은 본문 작성, 검토 담당은 근거 대조에 집중하도록 프롬프트와 출력 형식을 분리했다. 설정 담당 기본 모델은 `gpt-5.4-mini`, 창작·검토는 `gpt-5.4`다. 역할 분리는 작업 책임과 결과를 추적하기 쉽지만, 같은 모델이 작성과 검토를 맡아 비슷한 오류를 반복할 수 있다. 구현은 역할별 순차 실행이며 자유 토론이나 병렬 자율 에이전트 회의가 아니다. 다음 단계는 모델의 자유 판단이 아니라 `route()` 코드가 결정한다.

내 설명: “검토 결과에 따라 한 번만 수정하는 경로를 코드로 제한했습니다. 창작과 검토의 책임을 나누되, 작성자의 의도까지 자동으로 결정하지 않도록 했습니다.”

## 4. MCP — 무엇을 확인하고 무엇은 확인하지 못하나

MCP는 프로그램이 도구를 호출하고 결과를 받는 공통 규약이다. 현재 도구는 **`get_passages` 하나**다. 실행 기준 버전과 문단 키를 받아 저장된 문단을 반환한다.

읽을 순서는 다음과 같다.

1. `workflow.py:23`의 `verify_context()`가 현재 기준의 문단 키를 만든다.
2. `mcp_client.py:7`이 별도 Python MCP 서버 프로세스와 **stdio**로 연결한다. stdio는 표준 입력·출력을 통한 로컬 프로세스 간 통신이다.
3. `session.initialize()`로 연결을 초기화하고 `session.call_tool("get_passages", ...)`로 도구를 호출한다.
4. `mcp_server.py:10`은 SQLite를 `mode=ro`로 열어 읽기만 한다. 기준 스냅샷이 없거나 요청한 문단이 그 기준에 없으면 거절한다.
5. `verify_context()`가 반환된 문서·문단·텍스트를 기대한 스냅샷과 대조한다. 다르면 오류로 종료한다.

예를 들어 `docA:2:p003`은 문서 A의 2번째 버전에 있는 p003 문단을 뜻한다. `context_version`은 여러 문서·조건을 묶은 실행 기준의 ID로, 개별 문서 버전과 구분한다.

**현재 MCP는 기준의 전체 문단 키를 재조회한다.** 모델이 필요한 도구를 스스로 골라 호출하는 방식이 아니며, 조회 결과로 새로운 검색 맥락을 만들어 원래 맥락을 교체하는 방식도 아니다. 워크플로가 이미 가진 기준과 저장된 근거의 일치를 검사한다.

왜 단순 DB 함수 대신 MCP인가: 근거 조회를 공통 도구 인터페이스로 분리하고, 실제 연결·읽기 전용·잘못된 참조 거절을 구현하기 위해서다. 현재처럼 단일 로컬 프로그램에서는 직접 DB 조회도 가능하다. MCP는 프로세스 기동과 연결 실패 경로가 추가되는 비용이 있다. “MCP가 꼭 있어야만 가능한 기능”이라고 과장하지 않는다.

내 설명: “MCP로 실행 당시 기준 문단을 다시 읽어 스냅샷과 대조합니다. 문단이 실제 존재하는지는 확인하지만, 모델이 그 문장을 올바르게 해석했는지까지 보장하지는 않습니다.”

## 5. RAG — 미구현 이유를 설명하기

RAG는 관련 정보를 검색한 뒤 그 결과를 모델의 답변 맥락에 넣는 방식이다. 벡터 검색이 흔하지만 키워드 검색 등으로도 구성할 수 있다. **외부 자료를 읽었다는 이유만으로 모두 RAG는 아니다.**

LoreForge에는 현재 질의 기반 검색·임베딩·벡터 DB·검색 순위화가 없다. `main.py:234` 부근에서 입력·조건·채택한 설정·보존 쟁점의 기준 길이를 20,000자 이내로 제한하고, 기준 전체를 모델에 제공한다. 이 제한은 글자 수이며 토큰 수가 아니다. 실제 요청에는 지침과 검토 대상 등도 추가되므로 API 전체 입력이 20,000자라는 의미도 아니다.

선택 이유는 짧은 기준에서 멀리 떨어진 예외·회차 조건까지 함께 비교하기 위해서다. 일부 문단만 검색했을 때 예외를 빠뜨리는 문제가 생길 수 있고, 3일 MVP에서는 그 검색 품질까지 평가할 범위를 확보하기 어려웠다. 대신 기준이 길어질수록 비용·지연이 커지고, 전체를 줘도 모델이 모든 문장을 정확히 활용하지 못할 수 있다. 긴 원고는 범위를 줄여야 한다.

앞으로 RAG를 넣는다면 문단을 검색 단위로 만들고 문서·문단·회차·시점 정보를 함께 보관한다. 의심 문장뿐 아니라 관련 예외·반대 근거를 찾고, 찾은 문단을 기준 맥락에 넣는다. 검색 누락과 최종 오탐을 따로 평가해야 한다. 이것은 이후 계획이며 현재 구현이라고 말하지 않는다.

내 설명: “RAG는 이번 범위에 넣지 않았습니다. 짧은 기준 전체를 전달해 예외를 함께 비교하도록 했고, 긴 문서 지원에는 예외까지 찾는 검색과 그 평가가 필요합니다.”

## 6. 오탐 개선 — 프롬프트만 바꾼 것과 서버 검증을 구분

문제: 일반적인 동료 후보 소개와 특정 회차에서 불참한다는 설정을 모순으로 지적했다. 후보가 될 수 있다는 말은 모든 회차에 반드시 나온다는 말이 아니다.

`provider.py:9`의 `REVIEW_SCOPE_RULES`에 대상·회차·경로·시점·조건·후보/확정 사건을 먼저 구분하도록 적었다. “같은 회차의 축제에 오지 않는다”와 “그 회차의 축제 결승에 출전했다”처럼 적용 범위가 겹치고 양립하지 않을 때는 여전히 지적한다. 예외라는 단어가 있다고 서버가 모든 지적을 삭제하는 규칙은 없다.

검토 모델은 같은 호출 안에서 후보를 `unresolved`(남은 문제), `explained`(원문으로 해소), `optional`(선택적 상세화)로 판정하고 이유·근거를 낸다. 서버는 존재하는 문단인지와 필요한 반대 근거가 있는지를 검증하고 남은 쟁점을 표시한다. 적용 범위가 실제로 모순인지를 판단하는 부분은 여전히 모델에 의존한다.

공개 가상 회귀 10건은 정상 예외 6건과 실제 문제 4건으로 구성해 기대 분류·쟁점 수가 일치했다. 이는 관찰한 오류 유형을 재확인한 작은 검사다. 일반 정확도 100%나 모든 원고에서의 오탐 제거를 뜻하지 않는다. 상세 수치와 날짜는 [RESULTS.md](RESULTS.md)에 보존했다.

| 왜 JSON과 Pydantic을 쓰나? | 본문·항목·관계·근거를 구조화해 화면과 그래프가 같은 데이터를 쓰도록 한다. 형식·참조 검증과 이야기의 의미 검증은 다르다. 그래프만을 위한 추가 모델 호출은 없다. |
| 의존성 주입은 어디 있나? | `create_app(db_path=None, provider=None)`와 `build_workflow(store, provider)`가 외부에서 저장소·모델 호출 객체를 받는다. 테스트에서 임시 DB와 가짜 모델로 바꿀 수 있다. |
| 어디를 모듈화했나? | API는 `main.py`, 실행 순서는 `workflow.py`, 모델 호출은 `provider.py`, 문서 검증은 `documents.py`, 저장은 `store.py`, MCP는 client/server로 분리했다. 노드마다 별도 파일·서브그래프로 나눈 구조는 아니다. |
| LangSmith가 정확도를 높이나? | 선택한 실행의 역할·분기·MCP·사용량을 추적한다. 원인 분석에 도움을 주며, 추적 자체가 답변의 정답 여부를 검증하지는 않는다. 원문·응답 본문 대신 메타데이터를 전송하고 기본은 비활성이다. |
| 왜 수정 1회인가? | 무한 반복과 비용 증가를 막고 남은 판단을 작성자에게 넘기기 위해서다. 더 많은 수정으로 나아질 가능성을 포기하는 절충도 있다. |
| 최대 호출 수는? | 생성은 분석 1 + 초안 1 + 검토 1 + 수정 1 + 재검토 1 = 정상 최대 5회. 작업 전체의 일시적 오류 재시도는 1회로 제한해 최대 6회 시도다. 검토 전용은 정상 2회다. |
| `for range(2)`면 역할마다 한 번 재시도하나? | 아니다. 공유 `stats["retries"] < 1` 조건도 함께 검사하므로 작업 전체에서 한 번이다. 429·일부 5xx만 자동 재시도하며 타임아웃은 중복 청구 우려로 자동 재시도하지 않는다. |
| 새로고침하면 다시 생성하나? | 조회는 저장한 결과와 이벤트를 읽는다. 동일 요청 ID의 중복 시작은 기존 실행을 반환한다. 서버 재시작 당시 진행 중인 실행은 중단으로 남기고 자동 재호출하지 않는다. |
| SSE란? | 서버가 단계 진행 이벤트를 화면으로 보내는 방식이다. 이벤트 연결 자체가 모델 호출은 아니다. |
| 채택하면 문제도 사라지나? | 채택은 작성자의 선택이고 검토 문제 해결과 다르다. 미해결 쟁점을 보존하고, 다음 기준에는 채택한 최종본을 추가한다. 보류본과 수정 전 초안을 자동으로 추가하지 않는다. |
| 자동 테스트가 AI 품질도 보장하나? | 가짜 응답 테스트는 분기·상한·참조·저장을 재현 가능하게 검사한다. 실제 모델의 판단은 별도의 실제 API 사례로 확인한다. Python 105개·프런트엔드 17개는 2026-10-21 코드 검사 기록이며 이번 문서 수정에서 재실행한 수치가 아니다. |

## 8. 발표 직전 혼자 설명해 볼 질문

다음 여덟 가지에 파일을 보며 1~3문장으로 답한다. 막힌 부분만 위 해당 절로 돌아간다.

1. 사용자가 실행을 누른 뒤 어떤 순서로 결과가 만들어지는가?
2. `route()`의 세 조건 중 하나를 빼면 어떤 잘못된 동작이 생길 수 있는가?
3. 기존 설정 검토에서는 왜 `generate`와 `revise`를 실행하지 않는가?
4. 화면 관계도와 Agent Graph는 각각 무엇의 관계를 표현하는가?
5. MCP의 입력·출력은 무엇이며, 없는 문단을 요청하면 어디서 막히는가?
6. 현재 방식이 RAG와 다른 이유, RAG를 도입하면 새로 평가할 문제는 무엇인가?
7. 회차 예외와 실제 모순의 예를 각각 하나씩 들 수 있는가?
8. 실제 확인한 결과와 아직 보장하지 못하는 것은 각각 무엇인가?

발표 중에는 3~6절의 핵심만 설명하고, 보조 기술은 질문에 대비한다. 2분 지점에 코드 설명으로 넘어가는 대본 배분을 유지한다. 전체 API 파일과 테스트 결과를 모두 읽으려 하지 않는다.

## 9. 내 기여와 AI 지원을 설명하는 방식

주제, 키워드 시작, 생성·검토 분리, 원문에 있는 내용을 누락으로 지적한 문제, 관계도·본문 가독성 등은 내가 요구하고 결과를 판단한 내용이다. 세부 코드·프롬프트 작성과 검사 실행에는 AI 코딩 에이전트의 지원을 받았다. 독립적으로 전부 작성했다고 표현하지 않는다.

질문에는 “AI가 작성했습니다”로 끝내지 않고 **내가 고치려던 문제 → 해당 코드의 동작 → 선택 이유 → 확인한 결과와 한계** 순서로 답한다. 이해하지 못한 함수가 있다면 이해한 척하지 않고 해당 부분을 더 확인한다.
