# LoreForge 프로젝트 기획서

작성일: 2026-10-20 · 구현 기간: 2026-10-20~22, Asia/Seoul

프로젝트 이름은 **설정공방 · LoreForge**다. 아래 내용은 3일 MVP의 설계 기준이며, 현재 구현·검증 결과와 한계는 [구현 결과](RESULTS.md)를 따른다. 기존 생성 흐름의 로컬 웹·실제 OpenAI 연동을 확인했고 사람의 사용·창작 평가는 진행 중이다. 별도 작업 트리에서 검토 전용 흐름과 그래프 표시 범위를 구현했고 자동·타입·빌드 검사와 공개 원고 2건의 실제 API 검토·근거 이동을 확인했다. 그래프 배치의 최종 시각 점검과 새로고침 복원 점검은 별도로 남아 있다. 기존 main에는 병합·푸시하지 않았으며 상세 증거는 구현 결과에서 구분한다. 개인 발표를 하지 않을 가능성을 반영해 발표자료 제작·5분 리허설은 현재 필수 완료조건에서 제외하고 결과보고와 실행·검증 문서를 유지한다.

## 1. 한 문장 정의

**키워드 몇 개부터 기존 설정집까지, 흩어진 아이디어를 일관된 세계관으로 발전시키는 AI 창작 웹 서비스.**

## 2. 문제와 대상 사용자

대상은 소설·웹툰·게임의 스토리와 설정을 직접 만드는 개인 창작자다. 키워드나 메모를 발전시키려는 사용자는 ‘새 이야기 만들기’, 이미 쓴 원고의 문제를 확인하려는 사용자는 ‘기존 설정 검토’ 탭으로 시작한다. 두 작업은 원문 등록·분석·근거 저장 구조를 공유한다. 특정 작품이나 완성된 설정집이 없어도 시작할 수 있도록 만든다.

이 프로젝트에서 해결하려는 문제는 아이디어를 구체화하고 그 과정에서 설정을 일관되게 유지하는 일이다. 초기에는 흩어진 아이디어를 세계의 규칙·인물·갈등으로 연결하는 부담이 있고, 발전 단계에서는 어떤 내용이 단순 제안이고 무엇이 채택한 설정인지 구분하기 어렵다.

설정이 쌓이면 인물관계, 능력의 조건, 인물이 정보를 아는 시점, 사건의 인과관계를 함께 관리해야 한다. 긴 본문만으로는 관계를 다시 찾기 어려워, 본문과 연결된 그래프에서 주변 설정을 탐색할 수 있게 한다. 새 아이디어가 흥미롭더라도 이전 설정을 바꾸거나 필요한 설명을 빠뜨릴 수 있다. 한 번의 생성으로 얻은 결과를 창작자가 다시 원문과 대조해야 하는 부담이 핵심 문제다.

문제 정의에는 유명 작품의 사례를 짧게 참고한다. 죠죠는 가족관계 설정의 수정·사과 사례, 드래곤볼은 능력 규칙의 일관성 논쟁, 노블레스는 결말의 설명 부족에 관한 독자 비판으로 구분한다. 작품 비판을 서비스의 실제 효과로 제시하지 않는다. 출처와 한계는 [참고 자료](REFERENCES.md)에 정리했다.

### 해결하려는 작업

- 키워드·메모만으로도 첫 설정 초안을 만들 수 있다.
- 입력 재료, 명시적으로 지킬 조건, AI 제안, 사용자가 채택한 설정을 구분한다.
- 기존 설정을 근거로 새로운 인물·사건·분기를 구체화한다.
- 기존 원고는 새 글을 만들지 않고 검토하여 문제 위치·이유·수정 방향을 확인한다.
- 입력 조건·채택한 설정과의 충돌 또는 초안 내부 모순을 해당 근거와 함께 검토한다. 기준이 부족한 부분은 판단 불가나 질문으로 남긴다.
- AI의 대안을 창작자가 판단하고 채택한 결과를 별도로 보관한다.
- 인물·세력·장소·사건·규칙의 관계를 그래프에서 살펴보고 본문 근거와 검토 결과로 이동한다.

### 설계 원칙

- AI 검토는 창작자의 판단을 돕는 용도로 사용한다. 모든 설정 오류를 찾거나 이야기의 완성도를 보장하는 기능으로 보지 않는다.
- 반전·거짓말·인물 성장·의도된 설정 변경은 맥락을 확인한 뒤 판단한다.
- 원문 변경과 AI 제안의 채택은 창작자가 결정한다.

## 3. 입력 유형과 검증 시나리오

### 키워드로 시작하기

공개 예시: **무협 / 기억을 잃는 대가로 강해지는 무공 / 거짓말을 못 하는 주인공**. 별도 설정집이나 확장 요청 없이 입력할 수 있다. 설정 담당은 입력에 있는 재료와 조건만 정리하고, 창작 담당이 세계 규칙·인물·갈등을 포함한 초안 하나를 제안한다. 여러 대안 동시 생성과 긴 질문 인터뷰는 3일 범위에서 제외한다.

검토 담당은 입력 조건과 초안 내부의 모순·설명 부족을 확인한다. 사용자가 결과를 문서 단위로 채택하면 ‘이 설정 이어쓰기’로 다음 요청에 사용할 수 있다. 채택 전에는 초안의 내용을 기존 확정 설정이라고 부르지 않는다.

### 메모·설정집에서 확장하기

단편 메모나 기존 설정집도 같은 입력 경로로 처리한다. 검증에는 인물관계·능력의 조건·정보를 알게 되는 시점 등을 담은 짧은 공개용 가상 설정을 사용한다. 원문에 명시된 조건을 유지하면서 새로운 인물·사건을 구체화하는지 확인한다.

테스트 대상 작품을 미리 정하면 그 작품의 구조에 맞춰 기능을 만들기 쉽다. 따라서 이번 MVP는 특정 작품을 적용 대상으로 지정하지 않고, 키워드 시작·채택 후 이어쓰기·기존 설정 확장이라는 공통 흐름을 기준으로 개발한다.

### 기존 원고 검토하기

‘기존 설정 검토’에서는 원고 입력 → 분석 → 선택적 보호 조건 확인 → 검토 1회 → 쟁점 확인·검토 보고서 내보내기로 진행한다. 창작 담당 호출과 자동 수정은 실행하지 않는다. 입력 원문 스냅샷을 검토 대상으로 고정하며, 쟁점 유형·원문 인용·관련 조건 인용·이유·수정 방향을 먼저 보여주고 해당 문단으로 이동할 수 있게 한다. 사용자가 원고를 직접 고칠 수 있도록 돕되 제안을 자동 채택하거나 원문에 반영하지 않는다.

검토를 마쳤는데 쟁점이 없으면 이번 검토에서 발견된 쟁점이 없다고 안내한다. 검토 실패나 결과 누락과 구분하며, 원고의 정확성을 보증하지 않는다. 검토 실행에는 채택·보류·이어쓰기를 제공하지 않고 Markdown 검토 보고서를 내보낸다.

생성 흐름의 시연에서 보여줄 변화는 글의 길이가 아니라 다음 네 가지다.

1. 입력 재료·보호 조건·채택한 설정 중 무엇을 근거로 사용했는가.
2. 초안에서 어떤 충돌 후보나 설명 부족이 발견됐는가.
3. 수정본이 무엇을 바꿨고, 어떤 질문은 남겨두었는가.
4. 창작자가 어떤 제안을 채택·보류했고 그 이유는 무엇인가.

## 4. 3일 필수 범위와 수용 기준

데스크톱 브라우저에서 사용하는 웹 앱으로 만든다. 개발 중에는 Vue와 FastAPI를 로컬에서 실행하며, 웹 구현과 외부 배포를 구분한다. Obsidian 그래프의 탐색 방식은 참고하되 플러그인이나 데스크톱 앱은 만들지 않는다.

범위는 **로컬 사용자 1명, 새 작업당 입력 재료 1건, 선택적 요청 1개**다. 목적에 따라 ‘새 이야기 만들기’와 ‘기존 설정 검토’ 두 탭을 제공한다. 생성은 초안 1개·수정 최대 1회이며 검토 전용은 원고 검토 1회로 끝난다. 입력 형식별 별도 파이프라인이나 여러 프로젝트 관리 화면은 만들지 않는다. 작업 이력은 여러 건 저장하며, 채택 결과에서 이어쓰는 다음 작업은 사용자가 직접 시작한다.

| ID | 기능 | 완료를 판단할 조건 |
|---|---|---|
| F1 | 키워드·메모·본문 입력 | 키워드 몇 개만으로 시작 가능하다. 하나의 텍스트 입력창과 선택적 TXT·MD 가져오기를 제공하고 원문·버전·문단 ID를 보존한다. 새 작업의 빈 입력·제한 초과를 설명한다. |
| F2 | 재료·조건 확인 | 입력에서 정리한 후보를 실제 근거와 연결한다. 사용자가 반드시 지킬 조건을 직접 입력하거나 후보에서 선택할 수 있다. 선택은 필수가 아니며 AI 추론은 후보로만 남긴다. |
| F3 | 첫 설정·확장 생성 | 새 입력에서 요청이 비어 있으면 첫 설정 초안 하나를 만들고, 이어쓰기에서는 채택 설정의 다음 사건을 제안한다. 요청이 있으면 그 내용으로 구체화한다. 같은 실행 구조로 입력·선택 조건·채택 설정을 반영하고 새 제안을 구분한다. |
| F4 | 근거별 검토 | 생성 초안과 기존 원고 검토를 구분한다. 입력 조건·채택 설정과의 충돌에는 해당 기준과 검토 대상 위치를, 내부 모순에는 대상 문서의 대응 위치들을 표시한다. 검토 전용은 원문·조건 인용, 이유·수정 방향과 문단 이동을 제공한다. 설명 부족·판단 불가를 구분하고 없는 원문을 인용하지 않는다. |
| F5 | 제한된 수정 루프 | 생성 흐름에서만 수정 필요 시 1회 수정하고 재검토한다. 검토 전용에서는 생성·자동 수정을 실행하지 않는다. 한도 도달을 통과로 처리하지 않는다. 원문·초안·수정본을 보존한다. |
| F6 | 채택·보류·이어쓰기·내보내기 | 생성 결과를 문서 단위로 채택·보류한다. 검토 전용 결과에는 채택·보류·이어쓰기를 제공하지 않고 원문과 쟁점의 Markdown 보고서를 내보낸다. 채택한 최종 결과만 다음 작업의 기준 스냅샷에 포함할 수 있다. 보류 결과는 자동 포함하지 않는다. 원문·이전 기준은 보존하고 근거·남은 쟁점과 함께 내보낸다. |
| F7 | 진행·실패·이력 | 실행 단계, 소요 시간, 호출 수, 토큰을 표시한다. 오류를 성공과 구분하고 재시작 후 완료된 이력과 채택 상태가 유지된다. |
| F8 | 단일 생성 비교 — 보너스 목표 | 기능 완성 후 동일한 초안의 검토 전후를 비교하고 실패를 포함한 모든 실행 결과를 남긴다. 비교를 수행하지 못하면 결과보고서에 미수행으로 남긴다. |
| F9 | 문서 구조와 그래프 탐색 | 본문·항목·관계·근거를 공통 구조로 저장한다. 웹에서 확대·축소·이동·종류 필터·선택한 항목의 이웃 강조를 제공한다. 노드/관계 선택 시 상세·근거·검토 결과를 표시하고 입력·제안·채택 상태를 구분한다. |

입력 제한 초기값은 입력 재료·직접 입력한 보호 조건·이어받는 채택 설정을 합한 기준 본문 20,000자, 파일 100KB, 선택적 요청 2,000자다. 새 입력에서 요청이 비어 있으면 “이 재료로 세계 규칙·인물·갈등의 첫 설정 초안을 만들어줘”를 사용한다. 이어쓰기 요청이 비어 있으면 “채택한 설정을 지키며 다음 사건 하나를 구체화해줘”를 사용한다. 두 경우 모두 실제 요청을 기록한다. 실제 모델의 컨텍스트 한도와 출력 여유를 확인하고 초과 시 잘라서 숨기지 말고 입력을 줄이도록 안내한다. 큰 설정집 전체 처리는 후속 범위다.

### 우선 검증 항목

공개 가상 입력 1건의 LangSmith 추적으로 생성·검토·수정 단계를 확인해 실행 근거를 남긴다. Base 실습에서 실행 흐름 확인을 강조했기 때문에, 어떤 단계에서 검토와 수정이 일어났는지 보여주는 데 활용하려 한다. 추적은 기본 비활성이고 공개 입력 확인에만 켠다. 비공개 입력의 외부 추적은 기본으로 끈다.

### 선택 범위

- 문단별 차이 강조, 검토 필터, 소요 시간 시각화.
- 여유가 있으면 평가 케이스 반복 실행과 결과 집계 화면.

## 5. 사용자 흐름과 화면

- **새 이야기 만들기:** 재료 입력 → 후보·선택 조건 확인 → 첫 설정 또는 확장 생성 → 검토·최대 1회 수정 → 채택·보류 → 내보내기 또는 채택 설정 이어쓰기.
- **기존 설정 검토:** 원고 입력 → 분석·선택 조건 확인 → 검토 1회 → 쟁점과 원문 근거 확인 → Markdown 검토 보고서 내보내기.

목적 탭 아래의 공통 작업 화면을 세 영역으로 구성한다. 데스크톱에서 세 열로 보고 좁은 화면에서는 패널을 탭으로 전환한다. 긴 본문을 읽는 기능은 그래프와 함께 유지한다.

- **왼쪽 자료·목록:** “키워드나 설정을 자유롭게 적어주세요” 입력창, 파일 가져오기, 선택 조건, 인물·장소·사건 등 항목 목록, 실행 이력.
- **가운데 본문·그래프:** 입력/초안/수정본 버전 선택, 본문·그래프 보기 전환, 선택적 요청과 실행 상태. 그래프는 노드와 방향·이름이 있는 관계를 표시한다.
- **오른쪽 상세·검토:** 선택한 항목의 설명·근거 문단·검토 쟁점. 검토 전용은 쟁점 목록을 우선 표시하고 유형·원문/조건 인용·이유·수정 방향·문단 이동과 검토 보고서 내보내기를 제공한다. 생성 결과에는 문서 단위 채택·보류·내보내기를 제공한다. 채택 결과에서는 “이 설정 이어쓰기”로 이동한다. 노드 선택은 요청 입력을 도울 뿐 자동 실행이나 개별 설정 채택을 뜻하지 않는다.

화면은 딥 네이비 상단·자료 패널과 밝은 문서 영역으로 구성한다. 아이스 블루·파우더 블루는 보조 영역에, 사파이어 블루는 주요 버튼·선택 강조에 사용한다. 본문은 17~18px, 줄 간격 1.85, 최대 문서 폭 800px로 긴 글의 가독성을 확보한다. 좁은 화면에서는 자료·작업·상세 패널을 탭으로 전환한다.

### 그래프를 만드는 문서 구조

자유 입력은 그대로 보존하고, AI가 정리한 결과는 **본문 문단 + 항목 + 관계 + 근거 참조** 구조로 저장한다. 항목은 인물·세력·장소·사건·규칙의 5종이며, 관계에는 소속·등장·사용·제약·사건 선후 등의 의미와 방향을 붙인다. 문서 버전과 채택 상태는 서버가 관리한다.

설정 담당의 기존 분석 응답에 입력 항목·관계를, 창작 담당의 초안·수정 응답에 본문과 제안 항목·관계를 함께 담는다. 별도의 그래프 생성 에이전트나 추가 모델 호출은 넣지 않는다. 모델 출력 형식, 문서 예시, Markdown 내보내기 틀, 그래프 변환·검증 규칙은 [설정 문서 구조](SETTING_DOCUMENT_FORMAT.md)에 정의한다.

### 탐색 범위와 실패 처리

- 기본 그래프는 현재 선택 문서와 그 문서의 관계가 직접 참조하는 기준 문서의 끝점만 표시한다. 전체 기준 문맥은 별도 선택으로 펼치며 같은 이름이어도 문서별 ID를 유지한다. 다른 실행·분기를 전체 그래프로 자동 합치거나 이름으로 항목을 병합하지 않는다.
- 확대·축소·화면 이동·화면 맞춤, 종류별 필터, 노드/관계 클릭과 선택한 노드의 직접 이웃 강조를 제공한다. 관계 이름은 선택·마우스 올림 또는 전체 표시 선택 시 드러낸다. 화면 맞춤은 라벨까지 포함하며 패널 크기 변경에 대응하고 작은 최소 배율을 허용한다. 조작 도구는 그래프 캔버스 밖에 둔다. 초기 자동 배치는 하나만 사용한다.
- 입력에서 정리한 내용, AI 제안, 채택한 결과를 라벨과 선 모양으로 구분하고 색은 보조 수단으로 쓴다. 그래프 추출 결과 자체가 확정 사실이라는 뜻은 아니다.
- 검토 쟁점은 근거 문단이 겹치는 항목·관계에 연결한다. “충돌 후보”로 표시하고 이유를 함께 보여준다. 연결할 항목이 없는 지적은 검토 목록에 남긴다.
- 초기 검증 규모는 한 화면 30노드·60관계다. 더 큰 그래프는 표시 범위를 좁히도록 안내하고 표시/전체 개수를 보여준다. 본문이나 저장된 관계를 조용히 잘라내지 않는다.
- 관계가 없는 입력은 빈 그래프 또는 독립 노드로 표시한다. 잘못된 항목·근거·연결선은 그래프에서 제외하고 부분 표시 경고를 남긴다. 본문이 유효하면 읽기·검토를 계속할 수 있고 그래프 오류를 숨기지 않는다.
- 그래프와 같은 정보를 목록에서도 선택할 수 있게 해 키보드로 상세·근거를 확인한다. Canvas 선택만을 유일한 접근 경로로 만들지 않는다.

원문과 모델 출력을 HTML로 그대로 실행하지 않는다. 텍스트 또는 안전하게 처리한 Markdown으로 표시한다. 로딩·빈 결과·실패 상태를 각각 설명하고 버튼의 비활성 이유를 보여준다.

## 6. 에이전트와 실행 구조

| 역할 | 입력 | 책임과 출력 |
|---|---|---|
| 설정 담당 | 키워드·메모·본문, 이어받은 기준 | 입력에서 확인되는 재료·조건·설정 후보와 근거가 있는 항목·관계를 구조화한다. 부족한 설정을 이미 존재하는 사실처럼 채우지 않는다. |
| 창작 담당 | 입력·선택 조건·채택 설정·요청 | 첫 설정 또는 확장 초안 하나와 그 본문을 가리키는 항목·관계를 만들고 피드백에 따라 함께 수정한다. 기준 문서를 변경하지 않는다. |
| 검토 담당 | 동일 기준 스냅샷·조건·초안 또는 검토 원고 | 기준과의 충돌·초안 내부 모순·설명 부족·의도 확인 질문을 구분하고 실제 근거 위치를 연결한다. |

세 역할은 별도 프롬프트와 출력 계약을 가진 순차 단계다. 생성은 세 역할을 사용하고 검토 전용은 설정 담당의 분석과 검토 담당의 1회 검토만 사용한다. 설정 담당은 가벼운 모델, 창작·검토 담당은 품질 중심 모델로 나눈다. 창작과 검토는 같은 모델을 사용하므로 오류를 공유할 수 있다는 한계도 평가에 남긴다.

```mermaid
flowchart TD
    A[키워드 또는 메모 또는 설정집] --> B[설정 담당: 재료와 후보 정리]
    B --> C[사용자: 선택 조건 확인]
    C --> M{작업 목적}
    M -->|기존 설정 검토| R[검토 담당: 원고 검토 1회]
    R --> S[쟁점·원문 근거 확인 / 검토 보고서 내보내기]
    M -->|새 이야기 만들기| D[창작 담당: 첫 설정 또는 확장 초안]
    D --> E[검토 담당: 근거 확인]
    E --> F{수정 필요하며 한도 이내인가}
    F -->|예: 최대 1회| G[창작 담당: 수정]
    G --> H[검토 담당: 재검토]
    F -->|아니오| I[완료 또는 쟁점 남음]
    H --> I
    I --> V[본문과 관계 그래프에서 근거 탐색]
    V --> J[사용자: 채택 또는 보류]
    J --> K[별도 문서로 내보내기]
    J -->|채택 후 이어쓰기 선택| L[새 기준 스냅샷과 다음 요청]
    L --> B
```

### 기술 선택

- FastAPI·LangGraph·SQLite·Vue 3·SSE의 역할은 수업 Base에서 참고한다. 예제 폴더를 통째로 복사하지 않고 필요한 구조를 선별한다.
- OpenAI Python SDK와 Responses API로 연결하고 Pydantic 기반 구조화 출력을 사용한다. 형식 준수와 이야기 내용의 정확성은 별도 검증 대상이다. [공식 Structured Outputs 문서](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)
- 역할별 모델 ID는 `OPENAI_ANALYST_MODEL`(기본 `gpt-5.4-mini`), `OPENAI_WRITER_MODEL`과 `OPENAI_REVIEWER_MODEL`(기본 `gpt-5.4`)로 관리한다. 실제 호출에 사용한 모델과 usage를 기록한다. Day 1에 계정 접근 가능 여부·한국어 품질·지연·구조화 출력을 확인한다. 모델 실패를 다른 모델이나 모의 응답으로 자동 대체하지 않는다.
- 입력·조건·명시적으로 이어받은 채택 설정을 묶은 짧은 기준 스냅샷 전체를 생성·검토 단계에 제공한다. 자동 요약만을 유일한 근거로 사용하지 않는다. 초안의 새 설정은 이번 검토에서 기존 기준으로 소급하지 않는다.
- MCP는 **로컬 문단 저장소의 `get_passages(context_version, passage_ids)` 도구 1개**로 제한한다. 입력·보호 조건·채택 설정의 근거를 서버가 이 도구로 재조회해 표시한다. 초안 내부 모순의 위치는 해당 초안 버전에서 직접 검증한다. 이번 MCP 범위는 서버가 호출하는 근거 조회이며, 모델의 자율 도구 선택과 벡터 검색은 제외한다.
- 그래프 표시는 Vue 컴포넌트 안에서 Cytoscape.js를 사용한다. JSON 데이터·자동 배치·선택 이벤트를 활용하고 패키지 버전과 Vue 연동은 Day 1에 확인한다. [공식 문서](https://js.cytoscape.org/)
- 그래프 데이터는 SQLite에 문서 버전과 함께 JSON으로 저장한다. 그래프 뷰는 사람의 탐색 화면이며, 관련 설정을 검색하는 RAG나 GraphRAG를 추가하는 것은 아니다.
- 초기 MCP 도구는 읽기 전용이다. 원문은 보존하며 새 입력 버전 등록과 생성 결과의 채택 저장은 검증된 서버 코드가 처리한다.

### 수업 Base에서 바꿀 부분

| 기존 예제에서 확인한 동작 | LoreForge에서의 결정 |
|---|---|
| 운영 장애 분류·모니터링·런북 조회 | 창작 요청·원문 문단·설정 근거로 교체 |
| 글자 수와 번호 포함 여부 검사 | 근거·분기 조건·정보 시점 중심 검토로 교체 |

| 가상 단가로 비용 표시 | 실제 입력·출력 토큰 표시, 실제 청구액으로 표현하지 않음 |

| 실행 시 세션 DB 삭제·포트 프로세스 강제 종료 | 상태 보존, 포트 충돌 안내, 자신의 프로세스만 종료 |

## 7. 데이터와 상태의 최소 계약

- `Source`: 입력 원문(키워드·메모·본문), SHA-256 버전, 문단 ID. 원문을 보존하며 편집하면 새 버전을 만든다.
- `Context`: 입력 버전·직접 입력/선택한 조건·이어받은 채택 결과 ID와 본문을 담은 불변 기준 스냅샷. 각 근거 문단에 `input` / `constraint` / `accepted` 출처를 표시한다. 키워드만 있어도 생성할 수 있다.
- `Fact`: 내용, 종류, 근거 문단 ID, 적용 경로·시점, `explicit` 또는 `inferred`, 사용자 보호 여부. AI 추론과 추출 후보는 자동 확정하지 않는다.
- `StoryDocument`: 문서 ID·버전, 본문 문단, `entities`, `relations`, 근거 참조. 생성 형식과 서버 관리 필드는 [설정 문서 구조](SETTING_DOCUMENT_FORMAT.md)를 따른다.
- `GraphView`: 선택 문서와 참조 기준 끝점, 선택적으로 펼친 기준 문맥에서 조립한 표시 데이터, 문서별 상태, 연결된 쟁점, 표시 경고. 독립적인 원본 데이터가 아니다.
- `Run`: `mode: create|review`(생략 시 create), 기준 스냅샷 버전, 실제 요청, 모델·프롬프트 버전, 초안, 수정본, 검토 결과, 상태, 호출 수·시간·토큰.
- 검토 실행은 `mode`와 원고 스냅샷 `review_document`를 저장하며 `draft`·`revision`은 `null`이다. 원문을 새 생성 문서나 채택 기준으로 바꾸지 않는다.
- `Issue`: `conflict_candidate` / `internal_conflict` / `missing_explanation` / `intent_question`, 근거 종류·버전·위치, 이유, 수정 제안, 해결 상태. 외부 기준 충돌은 기준과 초안을, 생성 초안의 내부 모순은 서로 다른 두 문단 근거를 요구한다. 검토 전용은 한 문단 안에 모순되는 두 주장이 있으면 실제 문단 근거 1개와 두 주장을 설명한 이유를 허용하며, 같은 근거를 중복해 두 위치처럼 만들지 않는다. 기준이 없어 확인할 수 없는 내용은 판정 불가로 남기며 “설정 충돌 없음”으로 포괄 보증하지 않는다.
- `Decision`: `pending` / `accepted` / `deferred`, 대상 최종 결과, 선택 이유. 문서 단위 채택이며 개별 사실 편집 UI는 제외한다. 미해결 쟁점이 있으면 채택해도 지우지 않는다.

‘이 설정 이어쓰기’는 생성 실행에만 제공한다. 서버에서 생성 모드와 채택 상태를 확인하고 기존 기준+선택한 최종 결과로 새 스냅샷을 만든다. 수정 전 초안이나 보류 결과를 덧붙이지 않고 기존 스냅샷·이력은 바꾸지 않는다. 새 실행은 이 스냅샷을 고정해서 사용한다. 누적 기준이 입력 제한을 넘으면 자동 요약·누락 대신 범위를 줄이도록 안내한다.

실행 상태는 `running`, `completed`, `needs_attention`, `failed`, `interrupted`로 구분한다. 재시작 시 남아 있는 `running`은 `interrupted`로 표시하고 유료 호출을 자동 재개하지 않는다. 검토 결과가 없거나 출력 파싱이 실패하면 검토 통과가 아니다.

### API 인터페이스

API는 `/api` 접두사를 사용하며, 구현 계약은 [구현 기록](IMPLEMENTATION.md)에 정리한다.

- `POST /sources` 및 `GET /sources/{id}`: 키워드·메모·설정집 입력 등록과 복원.
- `POST /sources/{id}/analyze`: 입력 재료·설정 후보 정리.
- `POST /runs`: `mode: create|review`(기본 create), 분석 ID 또는 생성 결과를 이어쓸 채택 실행 ID, 선택 조건·선택적 요청으로 작업 시작. 검토 모드는 분석 ID를 사용하고 채택 실행을 이어받지 않는다. 서버가 기준 스냅샷을 만들고 목적에 맞는 실제 요청을 기록한다.
- `GET /runs`: 최근 실행 이력 조회.
- `GET /runs/{id}` 및 `GET /runs/{id}/events`: 결과와 SSE 진행 상태 조회.
- `GET /runs/{id}/graph`: 생성 실행의 초안·수정본 또는 검토 원고의 그래프 조회. 표시 범위는 선택 문서·참조 끝점이 기본이며 기준 문맥을 선택적으로 펼친다. 없는 수정본은 명시적으로 안내한다. 입력 분석 결과의 그래프는 analyze 응답과 저장된 입력 문서에서 제공한다. 조회·필터는 모델 호출을 만들지 않는다.
- `POST /runs/{id}/decision`: 생성 실행의 채택·보류 저장. 검토 실행의 결정·이어쓰기는 거절한다.
- `GET /runs/{id}/export`: 생성 결과 또는 검토 보고서 Markdown 다운로드.

SSE 재연결은 실행을 다시 만들지 않는다. 완료 결과는 GET으로 다시 읽을 수 있게 한다. MVP의 동시 실행은 1건으로 제한하며 중복 실행에는 현재 작업 상태를 안내한다.

## 8. 반복·실패·비용 통제

- 생성 작업의 준비 분석 1회, 초안 1회, 검토 1회, 필요할 때 수정 1회+재검토 1회: 정상 흐름 최대 5회 모델 호출. 그래프 데이터는 기존 분석·생성·수정 응답에 포함하고 별도 추출 호출을 추가하지 않는다. 분석 엔드포인트와 실행 엔드포인트는 같은 작업 예산을 공유하며 재사용 시 분석 비용을 중복 집계하지 않는다. 이어쓰기는 사용자가 시작한 새 작업으로 별도 기록한다.
- 검토 전용은 분석 1회+검토 1회로 정상 2회이며, 일시 오류 재시도 포함 총 3회 이내다. 창작·자동 수정·재검토 호출을 추가하지 않는다.
- 자동 재시도는 분석과 실행이 공유하는 작업 예산에서 1회만 허용하며 총 호출 시도 상한은 생성 6회·검토 3회다. SDK 내부 자동 재시도와 중복되지 않게 설정한다.
- 429·일시적 5xx에만 남은 재시도 예산을 쓴다. 인증·권한·입력 오류, 거절·불완전 출력은 설명하고 종료한다. 응답 여부가 불명확한 타임아웃은 자동 중복 호출하지 않는다.
- 초기 제한: 요청별 120초, 전체 실행 10분. 호출 횟수·출력 한도와 함께 Day 1 실측으로 조정하고 변경을 기록한다.
- API 키는 서버의 `.env`/환경변수에만 둔다. 문서 본문은 사용자가 실행한 작업을 위해 OpenAI API에 전달되며 입력 화면에서 이를 알린다. 웹 앱을 로컬에서 실행하더라도 모델 추론은 OpenAI API에서 수행한다.
- 모델 토큰 집계는 실제 응답의 usage를 사용한다. 비용을 표시한다면 확인 날짜가 있는 입력·출력 단가와 계산식을 명시하고 추정치로 표시한다. 초기 MVP는 금액보다 토큰·호출 수·시간을 우선한다.
- 문서 안의 지시는 설정 자료로 처리하고 실행 권한으로 사용하지 않는다. 임의 셸 실행·외부 페이지 탐색·원문 쓰기 도구는 제공하지 않는다.

## 9. 완료 기준과 한계

필수 F1~F7과 F9를 웹에서 확인하고 [평가 계획](EVALUATION.md)의 기능 검사를 수행한다. F8의 같은 초안 비교는 과제 보너스 목표이며 핵심 기능 안정화 뒤에 수행한다. 공개 입력 LangSmith 추적은 우선 검증 항목으로 시도 결과와 실패·미실행 여부를 남긴다. 원문 불변·근거 유효성·반복 상한·저장 복원은 코드 검증 대상이고, 이야기의 자연스러움과 창작 의도는 사용자의 판단 대상이다.

성공의 최소 조건은 키워드만으로 첫 설정을 생성·검토·채택하고 한 번 이어쓸 수 있으며, 기존 설정집을 생성 재료로 활용하거나 검토 전용으로 끝까지 사용할 수 있는 것이다. 검토 전용은 원문 보존·창작 담당 미호출·자동 수정 없음·근거 이동·보고서 내보내기·복원을 별도로 확인한다. 본문·그래프·근거를 연결하고 실패나 미해결 쟁점을 명시한다. 품질 향상은 실측 결과로 판단하며 개선되지 않았다면 그 결과와 추가 지연·토큰 비용도 결과보고에 기록한다. 특정 작가의 작품 전체를 평가할 수 있다거나 범용 고증 도구가 완성됐다고 주장하지 않는다.
