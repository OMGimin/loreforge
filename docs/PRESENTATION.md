## 발표 대본

### 1장. 설정공방 LoreForge — 00:00–00:20 / 20초

안녕하세요. SKALA 4기 광주캠퍼스 G074 김지민입니다. 과제 2로 세계관 창작과 설정 검토를 돕는 웹 서비스, 설정공방 LoreForge를 만들었습니다. 아이디어를 이야기로 확장하고, 충돌이 의심되는 부분은 원문 근거로 확인하는 서비스입니다.

### 2장. 주제와 세부 태스크 — 00:20–01:05 / 45초

이야기를 만들다 보면 인물과 사건이 늘어나면서, 앞의 설정과 뒤의 장면이 충돌하는지 확인하기 어려워집니다. 이를 세 가지 태스크로 나눴습니다. 첫째, 키워드와 유지 조건으로 초안을 만들고 검토합니다. 둘째, 이미 있는 원고는 다시 쓰지 않고 문제 위치와 이유부터 보여줍니다. 셋째, 관계도에서 연결과 근거를 확인하고, 채택한 최종본을 기준으로 이어씁니다. 생성과 검토를 별도 탭으로 나눈 이유도, 긴 글 전체를 매번 다시 읽는 부담을 줄이기 위해서입니다.

### 3장. 구현 결과와 검증 — 01:05–02:00 / 55초

두 화면은 공개 입력으로 얻은 실제 API 결과를 최신 화면에서 다시 연 것입니다. 왼쪽은 키워드로 만든 이야기의 수정본을 관계도로 본 화면입니다. 본문과 같은 데이터로 인물·장소·사건을 연결합니다. 오른쪽은 원문 검토입니다. 하나뿐인 열쇠가 같은 시각 서로 다른 장소에 있다는 내부 모순을 지적하고 원문 두 문단을 연결했습니다. 채택 후 이어쓰기까지 실제 흐름을 확인했고, 정상 예외 여섯 건과 실제 문제 네 건의 회귀 검사도 통과했습니다. 자동 검사와 타입·빌드도 확인했습니다. 다만 작은 회귀 표본이 모든 원고의 정확성을 보장하지는 않습니다. 이제 실행 코드를 설명하겠습니다.

### 4장. Agent Graph의 실행 경로와 종료 조건 — 02:00–03:00 / 60초

설정 분석 후 기준과 사용자 조건을 실행 상태에 넣고 LangGraph를 실행합니다. 생성 모드는 생성부터, 원문 검토는 검토 노드부터 시작합니다. 오른쪽 route 코드의 세 조건이 핵심입니다. 첫째, 검토 전용 모드가 아니어야 합니다. 둘째, revision이 없어야 합니다. 이 조건으로 두 번째 수정을 막습니다. 셋째, open 상태이면서 intent_question이 아닌 문제가 있어야 합니다. 작성자 의도 질문만 있으면 자동으로 답을 정하지 않습니다. 세 조건을 모두 만족하면 revise, 아니면 finish를 반환하고 조건부 연결이 다음 노드를 고릅니다. 수정 후에도 문제가 남으면 확인 필요로 종료합니다. 역할별 순차 실행이며 분석을 포함해 정상 최대 다섯 번, 재시도 포함 여섯 번으로 제한했습니다.

### 5장. MCP로 실행 당시 원문 근거 재조회 — 03:00–03:45 / 45초

MCP는 모델이 임의로 도구를 고르는 방식이 아니라, 워크플로가 기준 문단을 재조회하는 데 사용했습니다. 클라이언트에서 stdio 연결을 열고 세션을 초기화한 뒤 get_passages를 호출합니다. 서버는 SQLite를 읽기 전용으로 열고, 실행 당시 기준 버전과 문단 ID를 확인합니다. 기준에 없는 문단이면 오류를 반환합니다. 워크플로에서도 조회한 문단과 저장된 스냅샷이 같은지 대조합니다. 이 과정은 근거 위치와 원문의 일치를 확인하는 장치이며, 모델의 해석까지 옳다고 보장하지는 않습니다.

### 6장. RAG 적용 범위와 현재 기준 전달 방식 — 03:45–04:20 / 35초

RAG는 이번 MVP에 구현하지 않았습니다. 입력과 조건, 채택 설정 등의 기준을 이만 자 이내로 제한해 전체를 제공합니다. 일부만 검색하다 예외를 빠뜨리는 위험을 줄이기 위한 선택입니다. 대신 기준이 길어지면 입력 비용과 지연이 늘고, 긴 원고는 범위를 줄여야 합니다. 이후 검색을 추가할 때는 관련 문장뿐 아니라 예외까지 찾는지 함께 평가하겠습니다.

### 7장. 검토 오탐 보완과 남은 한계 — 04:20–04:45 / 25초

회차와 조건을 먼저 비교해 정상 예외와 실제 위반을 구분하도록 보완했습니다. 수정 한 번으로 반복과 비용은 제한했지만, 더 수정하면 해결될 문제도 남을 수 있어 작성자에게 넘깁니다. 지적이 없다는 결과도 정확성 보장은 아닙니다. 구현에는 AI 도구를 활용했고, 요구사항과 결과를 직접 판단했습니다. 감사합니다.

## 질문 대비 — 본 발표에는 읽지 않음

**RAG가 없는데 왜 MCP를 썼나요?**

MCP는 도구 호출 규약이고 RAG는 검색한 정보를 생성 맥락에 넣는 방식이다. 현재 MCP는 지정한 버전과 ID로 문단을 재조회한다. 벡터 검색과 검색 순위화는 구현하지 않았다. 기준 전체를 제공하는 MVP와 긴 문서의 검색 확장을 구분한다.

**에이전트들이 서로 토론하나요?**

역할별 프롬프트·출력 계약을 나눈 순차 실행이다. 설정 분석은 `gpt-5.4-mini`, 창작·검토는 `gpt-5.4`를 사용한다. 자율 회의나 병렬 토론을 구현했다고 말하지 않는다. 같은 모델의 역할 분리만으로 정확성이 보장되지는 않는다.

**무한 반복이나 중복 비용은 어떻게 막았나요?**

생성은 분석 포함 정상 최대 5회, 공유 재시도 1회를 합쳐 최대 6회 시도다. 원문 검토는 분석·검토 2회, 재시도 포함 최대 3회다. 수정본 유무로 두 번째 수정을 막고, 동일 요청 ID는 저장된 실행을 반환한다. 새로고침·그래프 조작은 모델을 재호출하지 않는다.

**그래프는 어떤 데이터를 사용하나요?**

본문·항목·관계·근거를 같은 구조화 응답에 저장한다. 문서 버전과 문단 ID를 연결해 본문·관계도·내보내기에 사용한다. 관계도는 Cytoscape.js 탐색 화면이며 GraphRAG가 아니다. 최신 화면은 항목 이름 16px 유지와 이름 간격 보정을 적용했다.

**LangSmith는 어느 부분에 썼나요?**

선택한 공개 실행에서 역할별 호출·분기·MCP·사용량을 추적했고 원격 API로 수신을 확인했다. 기본 추적은 꺼두며 원문·프롬프트·응답 본문을 전송하지 않는다. LangSmith 웹 화면 직접 확인과는 구분한다.

**검토 정확도 100%인가요?**

공개 회귀 10건에서 기대 분류와 쟁점 수가 일치했다는 뜻이다. 관찰한 오류 유형으로 만든 소규모 검사이므로 일반 정확도 100%로 표현하지 않는다. 한 실행에서 지적이 없다는 것도 모든 설정이 일관된다는 보장은 아니다.

**직접 한 부분과 AI 도움을 받은 부분은 무엇인가요?**

주제와 사용 흐름, 생성·검토 분리, 원문 대조와 가독성 문제를 제안하고 결과를 판단했다. 세부 코드·프롬프트 구현과 검사 실행은 AI 코딩 에이전트 지원을 받았다. 커밋 작성자나 저장소 소유만으로 모든 코드를 독립 작성했다고 설명하지 않는다.
