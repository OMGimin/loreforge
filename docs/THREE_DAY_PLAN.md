# LoreForge 3일 구현 계획

기간: **2026-10-20(화)~2026-10-22(목), Asia/Seoul**

현재 완료된 것은 기획 문서와 저장소 연결이다. 아래 개발·검증 항목은 아직 수행하지 않았다. 개인 구현을 기준으로 키워드 시작과 기존 설정 활용을 하나의 흐름으로 구현한다.

## 1. 이번 과제의 제출 방향

**신규 프로젝트 개발**로 제안한다. 수업 Base의 FastAPI·LangGraph·MCP·Vue 구조를 참고하되, 주제와 사용자 흐름은 세계관 만들기·확장·검토로 구성한다.

2026-10-20 오전 전사록 후반의 정정 안내를 일정에 반영했다. 현재 로컬 PDF의 14시 마감은 이전 안내다. **13시를 준비 기준으로 적용하되, 수정 PDF와 발표 세부 시각은 추가 확인이 필요하다.** 전사에는 인식 오류와 주변 대화가 섞여 있어 후반의 반복 안내를 우선 해석했다. 자료별 근거는 [참고 자료](REFERENCES.md)에 정리했다.

| 시점 | 제출·완료 기준 | 근거·확인 상태 |
|---|---|---|
| 10/20 17:00까지 | 선택 과제와 진행 계획 초안 등록. 정해지는 대로 먼저 등록하고 개발 가능 | 초기 PDF 및 오전 안내. 조기 등록 허용을 마감 폐지로 해석하지 않음 |
| **10/22 13:00까지** | **구현·결과보고 마무리, 공개 Git·보고서 주소 제출 준비** | 오전 전사 후반 정정 안내에 따른 준비 기준. 수정 PDF 대조 필요 |
| 반별 발표 순서 | **개인별 Zoom 5분**, 본인이 반영한 코드와 목적 설명 | 전사 후반 안내. 조는 발표 순서이며 팀 과제라는 뜻이 아님 |

기존 PDF의 17:30 발표 종료 표기는 수정본 확인 전에는 확정 시각으로 쓰지 않는다. 코드 저장소와 결과보고는 평가자가 공개 접근할 수 있어야 하며 GitHub Markdown 보고서도 가능하다. 강호행 전문을 공개할 필요는 없고, 공개용 가상 입력으로 재현 방법을 제공한다. 결과보고 형식 허용을 발표자료 면제라고 해석하지 않는다.

이 문서는 제출 준비 계획이다. 실제 원격 푸시·외부 제출·발표 자료 업로드는 해당 행위에 대한 사용자 승인 범위에서 실행하고 결과를 별도로 확인한다.

### 과제 등록용 요약

> 설정공방 LoreForge는 키워드 몇 개부터 기존 설정집까지, 흩어진 아이디어를 일관된 세계관으로 발전시키는 AI 창작 도구입니다. 설정 담당·창작 담당·검토 담당의 생성→검토→최대 1회 수정 흐름을 구현합니다. 처음에는 입력 조건과 초안 내부 모순을 검토하고, 사용자가 채택한 설정은 다음 확장의 기준으로 활용합니다. 공개 키워드로 시작하는 사례와 게임 강호행의 기존 설정 개선 사례를 구분해 보여줍니다. OpenAI API와 FastAPI·LangGraph·SQLite·Vue를 사용하고, 읽기 전용 MCP로 기준 문단을 조회합니다. 핵심 기능을 먼저 완성하고, 공개 입력의 실행 추적과 가능한 범위의 동일 초안 전후 비교로 구현·효과·한계를 설명합니다.

## 2. 구현 순서와 범위

데이터 계약 → 재료 입력 → 첫 설정 생성 → 검토·수정 → 채택·이어쓰기 → 저장·화면 완성 → 평가·발표.

[기획서](PROJECT_PLAN.md)의 **F1~F7이 필수**다. F8은 기능 안정화 후 수행하는 비교 평가 보너스 목표다. LangSmith 공개 입력 1건의 추적은 우선 검증 항목이다. 모든 기술 목록을 필수로 구현하거나 여러 시작 모드를 따로 만들지 않는다.

## 3. Day 1 — 키워드에서 첫 설정까지

목표: 기존 설정집 없이 키워드만으로 실제 OpenAI 응답을 받고, 메모·본문도 같은 입력 경로로 처리한다.

| 순서 | 작업 | 산출물 | 확인할 증거 |
|---|---|---|---|
| 1 | Base 구조 파악·로컬 환경 준비 | 설치·실행 안내, `.env.example`, 차용할 구조 메모 | 본인이 바꿀 역할·흐름을 설명 가능, 키가 화면·로그에 노출되지 않음 |
| 2 | 모델·구조화 출력 확인 | 모델 ID·usage·지연 기록 | 공개 키워드 입력으로 실제 응답 수집 |
| 3 | Source·Context·Fact·Run·Issue·Decision 계약 | 최소 모델·SQLite 모듈 | 입력·기준·AI 초안의 분리, 버전·문단 ID |
| 4 | 재료 입력과 후보·선택 조건 | F1·F2, 텍스트 입력창과 선택적 TXT·MD | 짧은 키워드와 기존 본문 모두 수용, 없는 근거를 만들지 않음 |
| 5 | 첫 설정 또는 요청에 따른 확장 | F3, 초안 저장 | 요청이 비어 있어도 기본 요청으로 실행, 새 제안 표시 |
| 6 | 최소 화면 연결 | 입력→후보 확인→생성→결과 화면 | 브라우저에서 실제 동작, 기준과 제안 구분 |

17:00 이전에 계획 초안을 등록할 수 있도록 기획서부터 준비한다. 등록 준비와 개발을 병행한다.

**Day 1 통과 기준**

- [ ] 공개 키워드 3개만으로 설정집·추가 요청 없이 첫 초안을 생성한다.
- [ ] 메모·본문 입력도 같은 화면과 파이프라인으로 처리한다.
- [ ] 반드시 지킬 조건은 선택 사항이며, 지정한 경우 실제 실행 입력에 남는다.
- [ ] AI의 추론·새 설정이 자동으로 채택된 기준에 들어가지 않는다.
- [ ] 키·모델·구조화 출력·usage를 실제 환경에서 확인하고 설치·재실행 방법을 기록한다.

**막히면:** 모델 비교·별도 입력 모드·여러 대안 동시 생성을 추가하지 않는다. 모의 응답으로 UI를 개발할 수 있지만 실제 API 검증 전에는 연결 완료로 표시하지 않는다.

## 4. Day 2 — 검토·수정·채택·이어쓰기

목표: 첫 설정과 기존 설정 확장 모두를 검토하고, 채택한 결과로 다음 요청을 한 번 실행한다.

| 순서 | 작업 | 산출물 | 확인할 증거 |
|---|---|---|---|
| 1 | 검토 역할과 근거 계약 | F4 | 기준 충돌은 기준+초안 위치, 내부 모순은 초안 두 위치, 근거 부족은 판단 불가 |
| 2 | 기준 문단 MCP 조회 | 읽기 전용 도구 1개 | 실제 stdio 호출로 입력·조건·채택 문단 확인, 잘못된 버전·ID 거절 |
| 3 | LangGraph 검토→수정→재검토 | F5 | 수정 최대 1회, 미해결은 `needs_attention` |
| 4 | SSE·실패 처리·결과 탭 | F7 일부 | 재연결로 새 실행이 생기지 않음, 시간·호출 수·토큰 표시 |
| 5 | 문서 단위 채택·보류·이어쓰기·내보내기 | F6 | 채택한 최종 결과만 새 기준에 포함, 원문·이전 버전 보존 |
| 6 | 이력·재시작 복원 | F7 | 선택 상태와 기준 버전 복원, 중단 작업의 자동 유료 재실행 없음 |
| 7 | 공개 입력 LangSmith 추적과 실제 사례 적용 | 실행 흐름 증거, 강호행 구간 1개 검토 | 공개 입력만 추적하고 비공개 자료 추적은 꺼짐, 채택 이유 기록 |
| 8 | 발표 뼈대와 코드 설명 위치 선정 | 5분 발표 초안 | 본인이 수정한 핵심 코드와 Base 차용 부분 구분 |

**Day 2 통과 기준**

- [ ] 키워드→생성→검토→채택→이어쓰기 1회가 동작한다.
- [ ] 기존 설정집에서도 보호 조건·근거를 확인하며 같은 흐름이 동작한다.
- [ ] 첫 생성에 기존 기준이 부족하다는 사실을 숨기거나 원문 인용을 만들어내지 않는다.
- [ ] 실제 지적이 없으면 억지 수정이나 오류 연출을 하지 않는다.
- [ ] 보류 결과·수정 전 초안이 다음 기준에 자동 편입되지 않는다.
- [ ] 검토 실패·한도 도달을 통과로 바꾸지 않고 미해결 쟁점을 채택 후에도 보존한다.
- [ ] 재시작 후 입력·기준·결과·선택을 복원하고 기존 DB나 다른 프로세스를 삭제하지 않는다.
- [ ] LangSmith 추적의 수행 여부·남은 설정 문제를 기록한다. 추적이 없어도 로컬 실행 상태는 확인 가능하다.

**막히면:** 관계도·토큰 단위 스트리밍·화려한 차이 강조를 제외한다. 문서 단위 채택과 결과 탭으로 충분하다. MCP가 지연되면 직접 저장소 호출로 전체 흐름을 먼저 검증하되 MCP 미구현 사실을 명시한다. 추적 설정 문제 때문에 핵심 생성·검토를 멈추지 않는다.

목표: **13:00까지 구현·결과보고를 마무리**한다. 발표는 5분 전체 안에 시연과 코드 설명을 포함하며 세부 배분은 [평가·발표 계획](EVALUATION.md)을 따른다.

| 시간대 | 작업 | 산출물 |
|---|---|---|
| 오전~10:30 | 핵심 기능·실패 경로 검사와 필수 오류 수정 | 실행 가능한 코드, 검사 결과, 미완료 항목 |
| 10:30~11:15 | 기능 안정 시 동일 초안 전후 비교 | 공개 입력의 비교 기록, 사람 판단·시간·토큰. 불가 시 미수행 명시 |

| 12:00~12:40 | README·결과보고·발표자료 마무리 | 공개 재현 방법, 보고서, 5분 발표자료 |

발표자료는 Day 2부터 준비한다. 12:00 이후에는 새 기능을 추가하지 않고 필수 수정과 보고·발표 준비만 한다. 13:00 뒤의 제출물 수정은 별도 안내를 확인하며, 발표 준비 시간을 구현 시간으로 잡지 않는다.

**Day 3 통과 기준**

- [ ] F1~F7의 완료·미완료와 F8 보너스 수행 여부를 구분한다.
- [ ] 공개 키워드와 가상 설정만으로 핵심 흐름을 재현할 수 있다.
- [ ] 실측 비교를 했다면 동일한 기준·초안의 결과, 호출 수·시간·토큰과 악화된 항목도 제시한다.
- [ ] 실제 강호행 결과와 의도적으로 만든 오류 시험을 구분한다.
- [ ] 개인 5분 안에 목적, 시연, 본인 코드, 평가·한계를 설명한다.
- [ ] 원문·키·비공개 로그가 공개 파일에 섞이지 않았는지 확인한다.
- [ ] 푸시·제출을 승인받아 실행했다면 원격 내용·공개 접근·제출 상태를 확인한다. 로컬 커밋을 제출 완료로 표시하지 않는다.

## 6. 일정이 부족할 때의 축소 순서

1. 꾸미기·문단별 diff·결과 집계 UI를 제외한다.
2. 추출 종류 자동 분류를 줄이고 재료·조건·근거 확인에 집중한다.
3. 모델은 하나, 초안도 하나로 유지한다. 다중 대안·긴 질문 인터뷰·개별 설정 편집기를 추가하지 않는다.
4. 보너스 평가는 공개 입력 A/B 1쌍부터 시작하고 여유가 있을 때 늘린다. 핵심 기능이 미완성이라면 비교를 미수행으로 남긴다.

**줄이지 않을 것:** 키워드만으로 시작, 입력·제안·채택의 분리, 채택 후 이어쓰기, 원문 보존, 실제 생성·검토, 유효한 근거, 수정 상한, 미해결 표시, 기본 실패 처리.
