# LoreForge 3일 구현 계획

기간: **2026-10-20(화)~2026-10-22(목), Asia/Seoul**

현재 완료된 것은 기획 문서와 저장소 연결이다. 아래 개발·검증 항목은 아직 수행하지 않았다. 개인 구현을 기준으로 순서와 우선순위를 정했으며 팀 구성이나 작업 가능 시간이 달라지면 범위를 조정한다.

## 1. 이번 과제의 제출 방향

**신규 프로젝트 개발**로 제안한다. 수업 Base의 FastAPI·LangGraph·MCP·Vue 구조를 참고하되, 주제와 사용자 흐름은 세계관 확장·검토로 구성한다.

과제 안내 PDF의 Day 1~3을 위 날짜에 대응했다. 공식 안내는 날짜 대신 Day 표기를 사용한다.

| 시점 | 제출·완료 기준 |
|---|---|
| 10/20 17:00까지 | 선택 과제와 진행 계획 초안 등록 |
| 10/22 14:00까지 | 구현 마무리, Git 주소와 결과보고서 주소 등록 |
| 10/22 17:30까지 | 반별 일정에 따른 결과 발표 |

이 문서는 등록용 내용을 준비한 것이며 실제 제출·원격 푸시·발표 자료 업로드는 별도 작업이다.

### 과제 등록용 요약

> 설정공방 LoreForge는 뿌리 스토리를 바탕으로 인물·사건·분기를 확장하고 설정의 일관성을 검토하는 멀티에이전트 창작 도구입니다. 유명 웹툰·애니메이션의 설정 충돌과 설명 부족 사례로 문제를 제시하고, 자체 게임 기획인 강호행을 실제 적용 대상으로 삼습니다. 설정 담당·창작 담당·검토 담당의 생성→검토→최대 1회 수정 흐름을 구현하고, 원문 근거·초안·수정본을 비교해 사용자가 채택할 수 있게 합니다. OpenAI API와 FastAPI·LangGraph·SQLite·Vue를 사용하고, 읽기 전용 MCP로 근거 문단을 조회합니다. 같은 입력의 단일 생성과 검토 루프를 비교해 설정 유지, 지적의 정확성, 지연시간·토큰 사용량 및 한계를 보고합니다.

## 2. 구현 순서

데이터 계약 → 원문 보존 → 단일 생성 → 검토 → 수정 루프 → 화면·저장 완성 → 평가·발표.

화면 장식이나 외부 연동보다 **원문 하나로 실제 생성하고 근거를 확인하는 흐름**을 먼저 완성한다. [기획서](PROJECT_PLAN.md)의 F1~F8이 필수 범위다.

## 3. Day 1 — 원문에서 초안까지 연결

목표: 작은 원문을 입력해 설정 후보를 확인하고 실제 OpenAI 응답으로 초안을 만드는 흐름.

| 순서 | 작업 | 산출물 | 확인할 증거 |
|---|---|---|---|
| 1 | 로컬 설정·패키지·서버 환경 준비 | 설치·실행 안내, `.env.example` | 키 없이 상태 확인 가능, 키가 화면·로그에 노출되지 않음 |
| 2 | 사용할 모델과 구조화 출력 확인 | 모델 ID 및 설정 기록 | 작은 공개 가상 설정으로 정상 응답·usage 수집 |
| 3 | Source·Fact·Run·Issue·Decision 계약과 SQLite 설계 | 모델·저장 모듈 | 원문 hash·문단 ID, 원문·초안의 분리 |
| 4 | 원문 등록·문단 분리·설정 후보 추출 | F1·F2의 최소 기능 | 각 후보의 근거를 확인, 보호 조건 선택 가능 |
| 5 | 확장 요청과 초안 생성 연결 | F3, 단일 생성 기준선 | 선택한 조건과 원문으로 초안 생성, 결과 저장 |
| 6 | 간단한 입력·결과 화면 | Vue 최소 화면 | 브라우저에서 입력→실행→결과까지 실제 동작 |

17:00 이전에 계획 초안을 등록할 수 있도록 기획서부터 확정한다. 개발 시간은 등록 준비와 병행한다.

**Day 1 통과 기준**

- [ ] 원문 입력과 문단 번호를 화면에서 확인한다.
- [ ] 실제 키를 서버에서 읽고 공개 가상 설정으로 유료 API 호출을 검증한다.
- [ ] 설정 후보의 존재하지 않는 근거 ID를 정상 결과로 저장하지 않는다.
- [ ] 한 번 생성한 초안과 모델·프롬프트 버전·usage가 남는다.
- [ ] 설치부터 재실행까지의 명령을 실제 환경에서 확인한다.

**막히면:** 모델 선택 비교는 중단하고 사용 가능한 한 모델로 고정한다. 먼저 TXT·MD와 붙여넣기만 지원한다. 가짜 응답으로 UI를 개발할 수는 있지만 실제 API 검증 전에는 완료로 표시하지 않는다.

## 4. Day 2 — 검토·수정과 사용자 선택 완성

목표: 초안을 근거로 검토하고, 필요한 경우 한 번 수정한 뒤 남은 문제까지 보여준다.

| 순서 | 작업 | 산출물 | 확인할 증거 |
|---|---|---|---|
| 1 | 검토 역할과 Issue 형식 구현 | F4 | 지적·원문 근거·초안 위치가 연결됨 |
| 2 | 원문 문단 MCP 조회 연결 | 읽기 전용 도구 1개 | 실제 stdio 호출로 ID와 본문을 확인하고 잘못된 ID를 거절 |
| 3 | LangGraph의 검토→수정→재검토 구현 | F5 | 수정 최대 1회, 미해결은 `needs_attention` |
| 4 | 단계별 SSE·실패 상태 처리 | F7 일부 | 재연결로 새 실행이 생기지 않음, 시간·토큰 표시 |
| 5 | 초안·수정본·검토 결과 화면 | 비교 화면 | 근거로 이동, 수정 전후를 확인할 수 있음 |
| 6 | 채택·보류·Markdown 내보내기 | F6·F7 | 원문 보존, 선택과 결과가 재시작 후 유지 |
| 7 | 강호행의 선택한 분기 1개 적용 | 비공개 실제 적용 결과 | 창작자가 보호 조건·채택 이유를 확인 |

**Day 2 통과 기준**

- [ ] 원문·초안·수정본이 별도 상태로 남는다.
- [ ] 충돌 후보·설명 부족·의도 확인 질문이 구분된다.
- [ ] 실제 지적이 없으면 억지 수정이나 오류 연출을 하지 않는다.
- [ ] 검토 실패·미해결·한도 도달이 통과로 바뀌지 않는다.
- [ ] 인증 오류·타임아웃·잘못된 JSON을 읽을 수 있는 메시지로 보여준다.
- [ ] 이력 조회와 채택 상태가 서버 재시작 후 복원된다.
- [ ] 종료·재기동 시 기존 DB나 다른 프로세스를 삭제하지 않는다.

**막히면:** 관계도·토큰 단위 스트리밍·화려한 차이 강조를 제외한다. 문서 단위 채택과 두 개의 결과 탭으로 충분하다. MCP 구현이 지연되면 직접 문단 저장소 호출로 전체 흐름을 먼저 검증하되, MCP 미구현 사실을 기술 범위에서 명시한다.

## 5. Day 3 — 평가·안정화·발표

목표: 14:00 전에 기능과 결과보고를 마무리하고 이후에는 발표 준비에 집중한다.

| 시간대 | 작업 | 산출물 |
|---|---|---|
| 오전 전반 | 핵심 기능·실패 경로 검사와 문제 수정 | 테스트 결과, 실행 가능한 코드 |
| 오전 후반 | 고정된 같은 입력으로 단일 생성/루프 비교 | 전체 실행 기록, 사람 검토표, 시간·토큰 비교 |
| 12:00~13:00 | 실제 강호행 결과의 채택·보류 이유 정리 | 전후 비교, 개선점·미해결 질문 |
| 13:00~14:00 | README·결과보고서 정리, 제출 준비 | 설치·실행 방법, Git·보고서 주소, 제출 체크 |
| 14:00~발표 전 | 시연 리허설·캡처·PPT 점검 | 5~7장 발표자료와 실패 시 대체 시연 자료 |

발표자료는 가능하면 Day 2부터 뼈대를 만든다. 14:00 이후에는 새 기능을 추가하지 않고 필수 오류 수정과 발표 점검만 한다.

**Day 3 통과 기준**

- [ ] F1~F8의 완료 여부를 사실대로 표시한다.
- [ ] 같은 입력·모델·제약 조건의 비교 결과와 호출 수·시간·토큰을 제시한다.
- [ ] 단일 생성보다 나빠진 항목이나 불확실한 판단도 포함한다.
- [ ] 공개용 가상 설정만으로 다른 사람이 핵심 흐름을 재현할 수 있다.
- [ ] 실제 강호행 결과와 인위적으로 만든 오류 시험을 구분한다.
- [ ] 원문·키·실행 로그가 커밋에 섞이지 않았는지 확인한다.
- [ ] 푸시·제출이 승인되어 실행됐다면 원격 내용과 제출 상태를 확인한다. 로컬 커밋만으로 제출 완료라고 하지 않는다.

## 6. 일정이 부족할 때의 축소 순서

1. 관계도, 꾸미기, 문단별 diff, 결과 집계 UI를 제외한다.
2. 추출 종류의 자동 분류를 줄이고 설정 후보와 근거 목록에 집중한다.
3. API 연결 제공자·모델은 하나만 유지한다. 여러 대안을 동시 생성하지 않는다.
4. 평가 반복은 기본 1쌍씩 수행하고, 여유가 있을 때 반복한다. 남은 불확실성을 보고한다.

**줄이지 않을 것:** 원문 보존, 근거 확인, 실제 생성·검토, 수정 상한, 미해결 표시, 채택·보류, 기본 실패 처리, 최소 전후 비교.

## 7. 개발 착수 시 결정할 항목

| 항목 | 현재 상태 | 결정 시점 |
|---|---|---|
| 모델 ID | 계정 가용성과 비용·지연 미검증 | Day 1 첫 연결 검증 |
| API 키 저장 | 사용자 보유, 아직 설정하지 않음 | 실제 구현·연결 단계에서 안전한 로컬 설정 절차 |
| 입력·출력·시간 제한 | 기획서의 초기 제안값 | Day 1 실측 후 필요한 범위만 조정 |
| 강호행 최종 보호 조건 | 뿌리 문서에서 후보 추출 가능 | Day 2 첫 실제 적용 전 창작자가 확인 |
| 공개할 강호행 결과 범위 | 원문·결과는 기본 로컬 | 공개 자료에 사용할 때 별도로 결정 |

이 항목들은 기획서와 저장소 연결을 막지 않는다. 실제 구현·유료 API 실행은 이번 기획 요청에서 수행하지 않는다.
