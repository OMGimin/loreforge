# 설정 문서 구조와 그래프 변환

작성일: 2026-10-20 · 상태: 구현 전 설계

설정집과 스토리는 **본문·항목·관계·근거**를 가진 공통 문서로 관리한다. 이 문서를 웹의 본문 보기와 그래프 보기에서 함께 사용한다. 그래프에 맞추려고 사용자에게 정해진 양식으로 입력하도록 요구하지 않는다. 키워드·메모·TXT·MD 입력은 그대로 보존하고, 정리·생성 결과부터 공통 구조를 적용한다.

## 1. 문서의 기본 틀

| 부분 | 내용 | 그래프에서의 역할 |
|---|---|---|
| 메타데이터 | 문서 ID·버전·제목·종류·채택 상태 | 버전 선택과 입력/제안/채택 라벨 |
| 본문 | ID를 가진 문단 목록 | 상세 읽기와 근거 이동의 원본 |
| 항목 | 인물·세력·장소·사건·규칙 | 그래프의 노드 |
| 관계 | 출발 항목·도착 항목·의미·조건 | 방향과 이름이 있는 연결선 |
| 근거 | 문서 버전·문단 ID | 관계를 클릭했을 때 보여줄 출처 |
| 검토 연결 | 근거가 겹치는 Issue ID | 관련 노드/관계의 쟁점 표시 |

문서는 읽기 위한 본문을 중심으로 둔다. 그래프는 본문에서 뽑은 관계를 보여주는 탐색 수단이다. 노드가 없거나 그래프 구성이 일부 실패해도 유효한 본문은 읽을 수 있다. 키워드만 있는 단계에서는 아직 구체화되지 않은 항목이나 관계를 억지로 만들지 않는다.

## 2. 서버와 모델의 책임

### 서버가 관리하는 값

- `document_id`, `version`, `schema_version`: 문서와 형식의 식별자. 본문이 바뀌면 새 버전을 만든다.
- `kind`: `input`, `draft`, `revision` 중 하나. 채택 여부와 구분한다.
- `decision`: 기존 Decision의 `pending`, `accepted`, `deferred`. 모델 응답으로 변경할 수 없다.
- `context_version`, `parent_document_ref`: 이번 작업의 기준과 이전 결과 연결.
- `graph_status`: `ready`, `partial`, `unavailable`. 그래프 상태와 Run의 검토 성공 여부는 별개다.

채택은 본문 전체에 대한 결정이다. 그래프 항목을 개별 채택하거나 사용자가 직접 연결선을 고치는 기능은 만들지 않는다. 입력 자료는 채택된 결과와 다른 상태로 표시한다. 채택한 결과라도 내부의 추론 표시와 미해결 쟁점은 유지한다.

### 모델이 반환하는 값

생성·수정 응답에는 `title`, `passages`, `entities`, `relations`를 함께 포함한다. 입력 분석은 원문에 서버가 붙인 문단 ID를 참조하고, 원문 본문을 다시 쓰지 않는다. 각 항목과 관계에는 `explicit` 또는 `inferred`를 표시한다. 여기서 explicit은 해당 문서에 명시되어 있다는 뜻이며, AI 초안의 내용이 기존 확정 사실이라는 뜻은 아니다.

| 구조 | 필수 필드와 의미 |
|---|---|
| Passage | `id`, `text`: 문서 안에서 유일한 문단 ID와 본문 |
| Entity | `id`, `type`, `name`, `description`, `basis`, `evidence`: 항목 ID·종류·이름·설명·명시/추론·근거 |
| Relation | `id`, `source`, `target`, `type`, `label`, `condition`, `basis`, `evidence`: 관계 ID·끝점·종류·읽을 이름·적용 조건·명시/추론·근거 |
| Evidence | `document_ref`, `passage_id`: 서버가 해석하는 문서 참조와 문단 ID |

항목 종류는 `person`, `group`, `place`, `event`, `rule`로 제한한다. 능력·기술의 사용 조건은 rule 항목에 담을 수 있다. 주요 관계 종류는 `belongs_to`, `appears_in`, `uses`, `constrained_by`, `precedes`이며, 나머지는 `related_to`와 의미가 드러나는 label을 사용한다. 사건 선후는 명시된 경우에만 연결하고 글에 나온 순서를 시간 순서로 가정하지 않는다.

`document_ref`의 `self`는 현재 생성 문서, 나머지는 서버가 요청에 제공한 기준 문서 참조다. 임의의 외부 문서 참조는 허용하지 않는다. 관계 끝점은 현재 문서의 항목 ID 또는 기준에서 제공한 전체 항목 ID만 사용할 수 있다. 사람 이름이 같다는 이유만으로 서로 다른 문서의 항목을 자동 병합하지 않는다. 기준 항목을 정확히 지정할 수 없으면 별도 제안 항목으로 남긴다.

## 3. 공개용 출력 예시

다음은 모델 응답 형식의 예시이며 실제 생성·검증 결과가 아니다. `condition`이 없으면 빈 문자열을 사용하고, 관련 항목이나 관계가 없으면 해당 배열을 비워 둔다.

```json
{
  "title": "폭풍 속 마지막 송신",
  "passages": [
    {"id": "p01", "text": "기록관 리나는 마지막 송신 사건의 담당자다."},
    {"id": "p02", "text": "마지막 송신에는 폭풍 중 송신할 수 없다는 규칙이 적용된다."}
  ],
  "entities": [
    {"id": "e1", "type": "person", "name": "리나", "description": "마지막 송신을 담당하는 기록관", "basis": "explicit", "evidence": [{"document_ref": "self", "passage_id": "p01"}]},
    {"id": "e2", "type": "event", "name": "마지막 송신", "description": "리나가 담당하는 송신 사건", "basis": "explicit", "evidence": [{"document_ref": "self", "passage_id": "p01"}]},
    {"id": "e3", "type": "rule", "name": "폭풍 중 송신 금지", "description": "폭풍 중에는 송신할 수 없다", "basis": "explicit", "evidence": [{"document_ref": "self", "passage_id": "p02"}]}
  ],
  "relations": [
    {"id": "r1", "source": "e1", "target": "e2", "type": "appears_in", "label": "담당한다", "condition": "", "basis": "explicit", "evidence": [{"document_ref": "self", "passage_id": "p01"}]},
    {"id": "r2", "source": "e2", "target": "e3", "type": "constrained_by", "label": "제약을 받는다", "condition": "폭풍 중", "basis": "explicit", "evidence": [{"document_ref": "self", "passage_id": "p02"}]}
  ]
}
```

이 예시는 `리나 → 담당한다 → 마지막 송신 → 제약을 받는다 → 폭풍 중 송신 금지`로 표시한다. r2를 선택하면 조건과 p02의 원문을 보여준다. 나중에 같은 버전의 초안에서 폭풍 중 송신하는 장면이 발견돼 검토 쟁점이 생기면, 실제 근거 참조가 겹치는 관계를 강조한다. 그래프 자체가 모순 판정의 정답은 아니다.

## 4. 본문·그래프·검토 연결 규칙

1. 서버가 본문 문단과 구조화 결과를 분리 검증하고 문서 버전을 붙인다. 입력 분석은 보존된 원문의 문단 ID만 사용한다.
2. 그래프 ID는 `document_id:version:entity_id`로 만든다. 관계 ID도 같은 방식으로 범위를 구분한다. 버전이 바뀌면 이전 결과를 덮어쓰지 않는다.
3. 그래프 화면에는 현재 실행에서 사용한 기준 문서들과 선택한 초안 또는 수정본만 조립한다. 모델은 제공된 기준 항목 ID를 끝점으로 참조할 수 있고, 서버는 허용된 ID인지 확인한다. 서로 다른 버전의 초안·수정본을 한 결과로 섞지 않는다.
4. 이름과 설명은 항목에서, 관계의 이름·방향·조건은 Relation에서 읽는다. 문서 종류·채택 상태는 서버 값으로 표시한다. 추출된 관계가 실제 본문에 의해 뒷받침되는지는 근거를 읽어 확인한다.
5. Issue의 근거와 항목/관계의 근거가 같은 문서 버전·문단을 가리킬 때 관련 쟁점으로 연결한다. 문단 단위 연결이라 범위가 넓을 수 있음을 상세 패널에서 알린다. 연결 대상이 없어도 쟁점은 검토 목록에 남긴다.
6. 채택하면 해당 문서의 상태 라벨을 갱신한다. 이어쓰기는 채택한 최종 결과와 기존 기준을 다음 작업의 스냅샷으로 가져오며, 원문·과거 그래프·과거 검토 결과는 보존한다.

같은 문서의 중복 항목 ID, 없는 관계 끝점, 다른 버전의 근거, 인용과 실제 문장의 불일치는 검증 오류다. 잘못된 항목·관계는 표시에서 제외하고 `partial`과 제외 수를 남긴다. 유효한 항목이 전혀 없거나 구조화 결과를 사용할 수 없으면 `unavailable`과 이유를 표시한다. 최상위 응답 파싱이나 본문 자체가 실패한 경우는 기존 Run 실패 처리에 따른다. 유효한 빈 배열은 관계 없음 상태이며 오류가 아니다.

초기 한 화면 표시 범위는 30노드·60관계로 잡는다. 그 이상은 목록에서 범위를 좁혀 탐색하며 표시/전체 개수를 알린다. 필터나 화면 제한으로 숨겨진 내용도 저장된 문서에는 남긴다. 모델이 모든 항목·관계를 추출한다는 보장은 없으므로 그래프를 설정집 전체의 완전한 목록이라고 표현하지 않는다.

## 5. Markdown 내보내기 틀

내부 기준 데이터는 JSON이며, 화면의 본문과 Markdown 파일은 이 데이터에서 만든다. Markdown을 다시 파싱해 그래프를 재구성하는 왕복 변환은 이번 범위에서 제외한다. 기존 MD 파일을 가져오면 일반 입력 자료로 분석한다.

내보내기는 다음 순서를 따른다. 제목·본문은 읽기 쉽게 유지하고 항목과 관계의 ID·근거는 뒤에서 찾아볼 수 있게 둔다.

1. 문서 제목, 문서 ID·버전·종류·채택 상태, 사용한 기준 버전.
2. 본문: 문단마다 `## passage-p01` 형태의 고유 제목과 원문.
3. 항목: `## entity-e1` 형태의 고유 제목 아래 이름·종류·설명·명시/추론·근거.
4. 관계 표: 출발·의미·도착·조건·근거. 내부 항목은 `[리나](#entity-e1)`처럼 연결한다.
5. 검토 결과와 미해결 질문, 채택·보류 이유.
6. 참조 근거: 현재 문서 밖의 근거는 `## evidence-1` 같은 부록 제목 아래 문서 ID·버전·문단 ID·인용을 표시한다. 전체 기준 원문을 자동으로 복제하지 않는다.

내부 근거 링크는 `[p01](#passage-p01)`, 기준 문서의 항목·문단은 내보낸 파일의 참조 부록으로 연결한다. 관계 표의 ID와 링크는 서버에서 생성해 누락된 앵커를 검사한다. 좌표·확대 비율은 내보내지 않는다. 자료 공유 전에는 근거 인용에 포함된 비공개 내용을 함께 점검한다.

## 6. 3일 안의 구현과 확인

- Day 1: 형식과 서버 검증, 공개 예제, 기존 모델 응답에 구조화 필드 포함, 본문/그래프 기본 표시.
- Day 2: 버전·상태 구분, 관계·근거 선택, 쟁점 강조, 채택·이어쓰기·Markdown 내보내기 연결.
- Day 3: 빈 그래프·잘못된 관계·버전 충돌·표시 한도·새로고침 복원·내부 링크를 확인하고 90초 시연에 반영.

별도 그래프 추출 호출을 추가하지 않아 정상 최대 5회·재시도 포함 최대 6회라는 기존 작업 예산을 유지한다. 구조화 필드로 출력량은 늘어나므로 Day 1에 출력 한도·지연을 확인한다. 그래프 표시나 필터는 API 호출이 아닌 저장된 데이터의 조작으로 처리한다.
